# Компилятор исходного языка

Компилятор принимает текст программы исходного языка и создаёт JSON-массив
инструкций для `cmd/sm`. Он не выполняет программу сам: выполнение, память
переменных, стек и ввод остаются задачей интерпретатора.

Путь данных выглядит так:

```text
program.l0 → лексер → токены → парсер → AST → генератор → code.json → sm
```

Например, для исходника:

```text
{x=2; y=3; write(x*y);}
```

компилятор создаёт:

```json
[
  {"CONST": 2},
  {"ST": "x"},
  {"CONST": 3},
  {"ST": "y"},
  {"LD": "x"},
  {"LD": "y"},
  {"BINOP": "*"},
  "WRITE"
]
```

## Сборка и запуск

```text
make build-compiler
make build

./compiler.exe -source program.l0 -output code.json
./main.exe -code code.json -input input.txt
```

У `compiler.exe` два режима аргументов:

```text
./compiler.exe -source program.l0 -output code.json
./compiler.exe program.l0 code.json
```

Если путь результата не указан, JSON печатается в стандартный вывод:

```text
./compiler.exe program.l0 > code.json
```

## 1. Лексер

Лексер находится в `internal/compiler/lexer.go`. Его функция `lex` проходит
исходный текст слева направо и создаёт срез `token`. Каждый токен содержит:

| Поле | Значение |
|---|---|
| `kind` | категория: идентификатор, число, символ или конец файла |
| `text` | исходный текст токена, например `"while"` или `"<="` |
| `line`, `column` | начало токена для сообщения об ошибке |

Для фрагмента:

```text
x<=10 && y!=0
```

получаются токены `x`, `<=`, `10`, `&&`, `y`, `!=`, `0`, а в конце добавляется
служебный токен конца файла.

Лексер распознаёт:

- идентификатор: первая буква — строчная латинская; далее разрешены буквы,
  цифры, `_` и `'`;
- десятичную константу;
- одиночные символы `{ } ( ) ; = + - * / % < >`;
- двойные операторы `!!`, `&&`, `==`, `!=`, `<=`, `>=`;
- однострочный комментарий от `--` до перевода строки;
- блоковый комментарий `(* ... *)`, в том числе вложенный.

Пробелы, табуляции и переводы строк не создают токенов. Нераспознанный символ
и незакрытый блочный комментарий завершают компиляцию с номером строки и
столбца.

## 2. Парсер и AST

Парсер находится в `internal/compiler/parser.go`. Это рекурсивный нисходящий
парсер: он хранит индекс текущего токена и использует три базовые операции:

- `current` возвращает текущий токен;
- `match` потребляет токен, только если его текст совпал с ожидаемым;
- `expect` требует конкретный токен и иначе возвращает понятную ошибку.

Разобранная программа не сразу превращается в JSON. Сначала создаётся AST —
внутреннее дерево программы. Его типы находятся в `internal/compiler/ast.go`.

Например, строка:

```text
x+=a*2
```

становится узлом `assignmentStatement` со значениями:

```text
name:     "x"
operator: "+"
value:    binaryExpression("*", variableExpression("a"), literalExpression(2))
```

Для операторов существуют отдельные узлы: `readStatement`, `writeStatement`,
`assignmentStatement`, `whileStatement`, `doStatement`, `forStatement`,
`ifStatement`, `blockStatement` и `skipStatement`.

### Разбор операторов

`parseStatement` выбирает способ разбора по первому токену:

| Первый токен | Метод | Результат AST |
|---|---|---|
| `read` | `parseRead` | `readStatement` |
| `write` | `parseWrite` | `writeStatement` |
| идентификатор | `parseAssignment` | `assignmentStatement` |
| `while` | `parseWhile` | `whileStatement` |
| `do` | `parseDo` | `doStatement` |
| `for` | `parseFor` | `forStatement` |
| `if` | `parseIf` | `ifStatement` |
| `{` | `parseBlockContents` | `blockStatement` |
| `skip` | прямо в `parseStatement` | `skipStatement` |

Точка с запятой после `read`, `write`, присваивания и `skip` необязательна:
её потребляет `parseStatement` после разбора простого оператора. У `do … while`
завершающая точка с запятой обрабатывается отдельно в `parseDo`. После блока
или другого составного оператора дополнительная точка с запятой не допускается.
Внешняя программа и каждый блок должны содержать хотя бы один оператор.

Заголовок `for` соответствует грамматике исходного L0:

```text
for (stmt expr ; stmt) stmt
```

Начало и шаг разбираются через обычный `parseStatement`, поэтому допускают
блоки, условия и циклы. У простых операторов в этих позициях сохраняется
необязательная точка с запятой; после выражения условия разделитель `;`
обязателен. Все три части заголовка обязательны. Например, допустимы обе формы:

```text
for (i=0 i<2; i+=1;) write(i);
for ({i=0;} i<2; {i+=1;}) write(i);
```

`elif` не имеет отдельного узла AST. Конструкция:

```text
if (a) write(1); elif (b) write(2); else write(3);
```

хранится как внешний `ifStatement`, чья ветвь `otherwise` содержит ещё один
`ifStatement`.

### Разбор выражений

`parseExpression` использует приоритеты. Чем выше число, тем раньше операция
связывает операнды:

| Приоритет | Операторы | Ассоциативность |
|---:|---|---|
| 1 | `!!` | левая |
| 2 | `&&` | левая |
| 3 | `==`, `!=`, `<`, `<=`, `>`, `>=` | неассоциативные |
| 4 | `+`, `-` | левая |
| 5 | `*`, `/`, `%` | левая |

Описание оператора возвращается функцией `binaryOperator` и включает
приоритет и ассоциативность. Поэтому `8-3-1` разбирается как `(8-3)-1`,
а `2+3*4` — как `2+(3*4)`. Все сравнения имеют один приоритет и не допускают
цепочек без скобок: `1<2<3` и `1<2==1` дают ошибку с позицией второго
оператора. Явное вложение `(1<2)<3` допустимо, как и независимые сравнения
в `1<2 && 3>2`. Все существующие бинарные операторы также разрешены
в составных присваиваниях, например `x<= =3`.

Скобки вызывают рекурсивный разбор отдельного выражения.
Знак `-` поддержан перед числовой константой, например
`-2147483648`; итоговое значение обязано помещаться в `int32`.

## 3. Генератор инструкций

Генератор находится в `internal/compiler/generator.go`. Он обходит AST и
добавляет элементы в `instructions`. После обхода `compiler.go` сериализует
этот срез в JSON. Даже для `skip` создаётся пустой массив `[]`, а не `null`.

Внутренний срез `[]any` нужен для смешанного JSON-формата. Инструкции без
операнда добавляются через `emit`, со строковым операндом — через
`emitString(opcode string, operand string)`, а константы — через
`emitConst(value int32)`. Элементы среза имеют только типы `string`,
`map[string]string` и `map[string]int32`.

Все методы обхода AST возвращают `error` и передают ошибки вложенных узлов
вызывающему коду. Неизвестный тип узла или неожиданный `nil` дают внутреннюю
ошибку компилятора с названием типа. Отсутствие ветви `else` обрабатывается
отдельно и ошибкой не является. При ошибке генерации `Compile` возвращает
`nil, error`, не сериализуя частично сгенерированные инструкции.

### Выражения

Любое выражение оставляет ровно одно значение на вершине стека.

| Исходное выражение | Генерируемые инструкции |
|---|---|
| `7` | `CONST 7` |
| `x` | `LD x` |
| `a+b` | `LD a`, `LD b`, `BINOP +` |
| `2+3*4` | `CONST 2`, `CONST 3`, `CONST 4`, `BINOP *`, `BINOP +` |

Генератор всегда сначала посещает левое выражение, потом правое и только затем
добавляет `BINOP`. Поэтому интерпретатор получает операнды в правильном
порядке.

### Простые операторы

| Исходник | Инструкции |
|---|---|
| `read(x)` | `READ`, `ST x` |
| `write(x)` | `LD x`, `WRITE` |
| `x=5` | `CONST 5`, `ST x` |
| `x+=5` | `LD x`, `CONST 5`, `BINOP +`, `ST x` |
| `skip` | нет инструкций |

Для составного присваивания генератор сначала загружает старое значение
переменной, затем вычисляет правую часть, применяет `BINOP` и сохраняет
результат обратно в ту же переменную.

### Условия и циклы

Метки имеют вид `L_<тип>_<номер>`. Номер увеличивается при каждой новой
метке, поэтому метки уникальны внутри программы.

`if (condition) thenBranch else elseBranch` генерируется по схеме:

```text
код condition
JZ else
код thenBranch
JMP end
LABEL else
код elseBranch
LABEL end
```

`JZ` снимает значение условия со стека. Ноль означает ложь и переводит
выполнение к `else`; любое ненулевое значение выполняет ветвь `then`.

`while (condition) body` генерируется так:

```text
JMP condition
LABEL body
код body
LABEL condition
код condition
JNZ body
```

Первый `JMP` не позволяет выполнить тело до первой проверки. `JNZ` возвращает
в тело, только когда условие ненулевое.

`do body while (condition)` отличается порядком:

```text
LABEL body
код body
LABEL condition
код condition
JNZ body
```

Поэтому тело выполняется хотя бы один раз.

`for (initial condition; post) body` разворачивается генератором в:

```text
код initial
while (condition) {
  код body
  код post
}
```

## Файлы

### `cmd/compiler/main.go`

Командная оболочка. Разбирает аргументы, читает исходный файл, вызывает
`compiler.Compile` и записывает JSON в stdout или файл. Ошибки чтения,
компиляции и записи печатаются в stderr, а процесс завершается кодом `1`.

### `internal/compiler/compiler.go`

Публичная функция `Compile`. Связывает все этапы: вызывает лексер, создаёт
парсер, запускает генератор и сериализует результат через
`json.MarshalIndent`.

### `internal/compiler/token.go`

Определяет `token`, категории токенов и вспомогательные функции для проверки
символов идентификатора и форматирования ошибок.

### `internal/compiler/lexer.go`

Реализует проход по тексту и создание токенов. Это единственное место, где
компилятор понимает символы комментариев и исходное расположение символов.

### `internal/compiler/ast.go`

Содержит закрытые типы синтаксического дерева. Парсер создаёт эти структуры,
а генератор читает их; другие пакеты не зависят от их устройства.

### `internal/compiler/parser.go`

Реализует грамматику языка: блоки, операторы, выражения, приоритеты и
диагностику синтаксических ошибок.

### `internal/compiler/generator.go`

Преобразует AST в инструкции стековой машины и создаёт метки для переходов.

### `internal/compiler/compiler_test.go`

Интеграционные тесты: читают `tests/testdata/sources.json`, компилируют каждый
исходник, запускают его через существующий интерпретатор и сравнивают вывод.
Для ошибочных выполнений проверяют конкретную причину и соответствие
диагностики возвращённой ошибке. Также проверяют несколько ошибочных
исходных программ и позицию ошибки в цепочках сравнений.

Каталог `tests/testdata/compiler_syntax.json` содержит синтаксические случаи
с полями `name`, `source`, `valid`, `output`. Go-тесты компилируют каждый
случай и проверяют результат выполнения с вводом `0`; для недопустимого
исходника требуют ошибку и отсутствие JSON. Скрипт `scripts/reference.cjs`
проверяет этот же каталог в обоих режимах исходного L0: `eval` и `sm`.
Текст ошибки L0 и точная последовательность инструкций не сравниваются.
Каталог не изменяет существующие эталонные программы и файловые фикстуры.

### `internal/compiler/generator_test.go`

Внутренние тесты проверяют отказ для неизвестных типов и `nil`, а также
передачу ошибок из вложенных блоков, выражений, условий и циклов.

### `Makefile`

Цель `build-compiler` собирает `./cmd/compiler` в `compiler.exe`. Цель `build`
по-прежнему собирает интерпретатор.

### `.gitignore`

Строка `/compiler.exe` исключает собранный компилятор из Git.
