# AST-интерпретатор, компилятор и стековая машина на Go

И интерпретатор, и компилятор принимают **готовый JSON AST** языка L0.
Исходный текст разбирает только референс преподавателя:

```text
program.l0 → референс Docker / L0.js → program.json
                                       ├─ AST-интерпретатор → результат
                                       └─ наш компилятор → code.json → стековая машина → результат
```

`program.json` в обоих путях имеет один формат — JSON AST референса.
`code.json` — другой формат: массив инструкций стековой машины. Собственного
парсера исходного языка больше нет. Генератор SM находится в `internal/compiler`,
его точка входа — `cmd/compiler/main.go`.

## Запустить готовый AST

Для сборки нужен Go 1.27.1+. Внешних Go-зависимостей нет.

```sh
make build-interpreter
./interpreter.exe -code program.json -input input.txt
./interpreter.exe -code program.json -input input.txt -output result.txt
```

Оба входных пути обязательны. Без `-output` результат идёт в stdout без
завершающего перевода строки. Ошибки идут в stderr с ненулевым кодом завершения;
при ошибке программы существующий файл результата не изменяется.

AST можно скачать из поля **JSON representation** на странице
[Simple Imperative Language Reference Interpreter](https://dboulytchev.github.io/eval.html).
Пример `program.json`:

```json
{"seq":{"left":{"read":"x"},"right":{"write":{"var":"x"}}}}
```

Для `input.txt` со значением `[1,"hello",[]]` результат — `[1; hello; []]`.
Ввод — значения через запятую; без `read` можно передать пустой файл. Строки ввода
используют удвоенные кавычки (`"a""b"`), а JSON AST — стандартное JSON-экранирование.

Готовый AST также запускается через Makefile, если установлен Node.js:

```sh
make run AST=program.json INPUT=input.txt
make run AST=program.json INPUT=input.txt OUTPUT=result.txt
```

Этот вариант не обращается к референсу и не требует Docker или `L0.js`.

## Получить AST из исходника и запустить

Для make-команд обработки исходников дополнительно нужен Node.js. Референс
выбирается переменной `REFERENCE`: `docker` по умолчанию либо `web`.

```sh
make ast SOURCE=program.l0 AST=program.json
make run SOURCE=program.l0 INPUT=input.txt
make run SOURCE=program.l0 INPUT=input.txt OUTPUT=result.txt
```

`make ast` только получает и сохраняет AST. Если `AST` не указан, используется
`.cache/program.ast.json`. `make run SOURCE=...` создаёт временный AST, запускает
наш интерпретатор и удаляет временные файлы. Одновременно задавать `SOURCE` и `AST`
для `make run` нельзя. `INPUT` обязателен; `OUTPUT` необязателен.

Пути с пробелами передавайте в кавычках:

```sh
make run SOURCE="examples/my program.l0" INPUT="examples/my input.txt"
```

### Docker-референс

Нужен запущенный Docker с поддержкой `linux/amd64`. Версия образа закреплена:

```text
dboulytchev/pl-platforms@sha256:14acc7b02e71c0a9c69e4bfe9a0aed57e8e2e7e3c0bc6b75131cd489fd66e1dd
```

При первом обращении отсутствующий образ скачивается автоматически. Прогресс
скачивания идёт в stderr, stdout остаётся результатом программы. Платформу,
образ и путь к Docker при необходимости можно переопределить:

```sh
make ast SOURCE=program.l0 AST=program.json REFERENCE_PLATFORM=linux/amd64
make ast SOURCE=program.l0 AST=program.json REFERENCE_IMAGE=dboulytchev/pl-platforms:latest
```

По умолчанию контейнер выдаёт **AST**, флаг `-compile` не используется. Исходник
передаётся через stdin, без подстановки в shell-команду. Проверяются код завершения,
stderr и JSON: контейнер может сообщить ошибку, вернув код 0. При ошибке старый AST
сохраняется; замена файла выполняется только после получения корректного JSON.

### Референс сайта

Этот вариант использует оригинальный `L0.js` локально в Node, без Docker и без
автоматизации браузера:

```sh
make reference-js
make ast SOURCE=program.l0 AST=program.json REFERENCE=web
make run SOURCE=program.l0 INPUT=input.txt REFERENCE=web
```

`make reference-js` скачивает текущий bundle сайта в `.cache/L0.js`. Для уже
скачанной или закреплённой версии:

```sh
make run SOURCE=program.l0 INPUT=input.txt REFERENCE=web REFERENCE_JS=/path/to/L0.js
```

Обёртка останавливает референс при получении AST: исходная программа при этом
**не исполняется**. Даже AST бесконечного цикла можно получить без его запуска.
Выполнение делает наш интерпретатор в `make run` либо наша стековая машина
после нашего компилятора в `make run-sm`.

Версию Docker и текущую версию сайта нельзя считать одинаковыми. Например,
обновлённый сайт сохраняет внешние кавычки строковых литералов внутри значения
AST, а закреплённый образ использует прежнее представление. Обёртка не исправляет
и не преобразует AST: наш интерпретатор исполняет ровно полученное дерево.

## Устройство интерпретатора

AST, JSON-декодер и выполнение находятся в `internal/interpreter`. Общий пакет
`internal/runtime` содержит значения, операции, разбор ввода и форматирование;
его используют и AST-интерпретатор, и стековая машина. Внешний API:

```go
func Run(programJSON []byte, input io.Reader, output io.Writer) error
```

`runtime.Value` — псевдоним `any`: число `int32`, изменяемая строка `[]byte` или
ссылка на закрытый объект массива с элементами `[]any`.
Присваивание сохраняет общую ссылку. Длина и индексы строки считаются в байтах.
Чтение строки по индексу возвращает код байта 0…255; запись принимает число в этом
диапазоне. Массив имеет фиксированный размер, элементы могут менять тип. Каждое
выполнение литерала создаёт новый объект, в том числе внутри цикла.
Вывод сохраняет значения со ссылками и форматируется после успешного завершения;
поздняя мутация влияет на ранее выполненный `write`.

Согласованные отличия от исходного референса: исправленный строковый ввод,
разрешённый пустой ввод и пустые массивы. Циклические массивы можно хранить,
но при обнаружении цикла во время вывода/сравнения возвращается `ERROR: cyclic array`.
Повторная ссылка на один объект без цикла допустима: `[a, a]` выводит его дважды.

## Компилятор и стековая машина

Для компиляции **того же AST**, который принимает интерпретатор, в инструкции
стековой машины:

```sh
make build-compiler
./compiler.exe -code program.json -output code.json
```

Для выполнения полученных инструкций:

```sh
make build
./main.exe -code code.json -input input.txt
./main.exe code.json input.txt
```

`code.json` — массив команд `READ`, `WRITE`, `CONST`, `LD`, `ST`, `BINOP`, `LABEL`,
`JMP`, `JZ`, `JNZ`, `STRING`, `ARRAY`, `LENGTH`, `ELEM`, `SET`. Стек и переменные
хранят общие значения. Компилятор поддерживает узлы AST `const`, `var`, `binop`,
`string`, `array`, `length`, `elem`, `read`, `write`, `assn`, `set`, `seq`, `if`,
`while`, `do`, `"skip"`.
`for`, `elif` и составные присваивания уже развёрнуты референсом в эти узлы.

Стек в таблице записан от основания к вершине, вершина справа:

| Команда JSON | Изменение стека |
|---|---|
| `{"STRING":"abc"}` | `[…] → […, строка]`, новый объект при каждом выполнении |
| `{"ARRAY":n}` | `[…, e₀, …, eₙ₋₁] → […, [e₀, …, eₙ₋₁]]` |
| `"LENGTH"` | `[…, объект] → […, длина]` |
| `"ELEM"` | `[…, объект, индекс] → […, элемент]` |
| `"SET"` | `[…, объект, индекс, значение] → […]`, изменение объекта |

`ARRAY` принимает неотрицательный `int32`; `ARRAY 0` создаёт пустой массив.
Массив копирует элементы из участка стека в своё хранилище, сохраняя ссылки на
вложенные объекты. `STRING` допускает пустую строку. Текст AST и `STRING` используется
буквально: кавычки, уже находящиеся внутри значения, не удаляются.

Арифметика, логические операции и условия переходов требуют `int32`. Сравнения
строк выполняются по байтам; массивов — сначала по длине, затем по элементам.
Несовместимые типы дают ошибку, сложение строк и массивов не поддерживается.

API стековой машины:

```go
func NewStackMachine(code []byte) (*StackMachine, error)
func (m *StackMachine) Run(input io.Reader, output io.Writer) error
```

Ввод полностью разбирается до исполнения. `WRITE` накапливает значения со ссылками;
вывод появляется после успешного завершения, через `; `, без завершающего перевода
строки. При runtime-ошибке вывода нет. Повреждённый UTF-8 отображается с заменами,
соответствующими браузерному `TextDecoder`. Пакеты возвращают ошибки; CLI печатает
сообщение один раз в stderr и возвращает код 1. Номер инструкции больше не добавляется
к runtime-сообщению; нехватка стека — `ERROR: stack exhausted`.

API компилятора:

```go
func Compile(programJSON []byte) ([]byte, error)
```

Без `-output` компилятор пишет SM JSON в stdout. Ошибки идут в stderr с кодом 1;
при ошибке компиляции существующий файл SM-кода не меняется. Флаг `-source` удалён.

Через Makefile можно отдельно сохранить SM-код или сразу его выполнить:

```sh
make compile AST=program.json CODE=code.json
make run-sm AST=program.json INPUT=input.txt
make run-sm AST=program.json INPUT=input.txt OUTPUT=result.txt
```

Без `CODE` команда `make compile` сохраняет инструкции в `.cache/program.sm.json`.
`make run-sm` использует временный файл инструкций и удаляет его после выполнения.
При ошибке результат не записывается, существующий `OUTPUT` сохраняется.

Для этих же команд вместо `AST` можно указать `SOURCE`. Тогда перед нашим
компилятором исходник разбирает выбранный внешний референс:

```sh
make compile SOURCE=program.l0 CODE=code.json
make run-sm SOURCE=program.l0 INPUT=input.txt
make run-sm SOURCE=program.l0 INPUT=input.txt REFERENCE=web
```

В обоих случаях выбирается ровно один вход: `SOURCE` или `AST`. `INPUT` нужен
для запуска, но не для компиляции. Docker вызывается без `-compile`: генерацию
SM выполняет наш компилятор.

## Эталон и порядок вычислений

Основной эталон поведения — [sm.html](https://dboulytchev.github.io/sm.html).
Оба наших пути используют его порядок:

- Бинарное выражение: левый операнд, затем правый. Логические операции вычисляют оба.
- Массивный литерал: элементы слева направо.
- Чтение элемента: объект, затем индекс.
- Запись элемента: объект, индекс, значение.

Операнды вычисляются до проверки типов и границ. Внутри арифметической операции
сначала проверяется тип правого операнда; для индексации — тип индекса.

На сайте `eval.html` порядок отличается: бинарные выражения вычисляются справа
налево, чтение элемента начинает с индекса, запись — со значения. Например,
`left-right` сообщает об отсутствии `right` в eval и `left` в SM. Наш AST-интерпретатор
теперь следует SM, чтобы оба наших пути совпадали. Также новая версия сайта добавила
`is` в сообщение `array/string value expected` при чтении элемента и `.length`.

Старый корпус `tests/testdata/interpreter/reference.json` сохранён без изменений.
Восемь новых ожиданий проекта перечислены явно в `sm_expectations.json` рядом с ним:
пять для первой ошибки и три для изменённого текста диагностики.

## Проверки

```sh
make test
make test-workflow
make test-cases
```

`make test` запускает все Go-тесты, включая 127 сохранённых примеров AST-интерпретатора.
На всех 127 AST проверяются оба пути выполнения. Ещё 32 AST
в `tests/testdata/compiler_ast.json` проверяют переходы и вложенные циклы/ветвления
компилятора; версия `L0.js`, выдавшего эти деревья, закреплена SHA-256 в файле.
`make test-workflow` проверяет make-команды, обёртки референсов, обработку ошибок и
пути с пробелами, используя локальные подмены без Docker и сети. Нужны Go и Node.

`tests/testdata/sm_reference.json` содержит 149 примеров текущего SM-референса:
исходник, AST, инструкции, ввод, Output и Message. На каждом примере проверяются
наш компилятор, исполнение команд самого референса и AST-интерпретатор. Наблюдения
`eval.html` сохранены рядом, включая расхождения первой ошибки. Три исходника,
которые новая версия парсера отвергает, перечислены отдельно.

Все команды: `make help`.
